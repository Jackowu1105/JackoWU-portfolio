## Problem Definition

Controllers mentally categorize flights by aircraft size first, as it determines resource allocation — how many PTS (Passenger Transport Services) events a flight needs, and what ground crew and equipment to mobilise. Bay type (Remote Stand vs. Frontal Stand) then determines the logistics: remote stands need bus services, frontal stands have jet bridges.

The existing interface required controllers to expand individual flights to reach this information. During peak hours — when every second counts and the board is scanned every 2-3 minutes — that extra click broke the scanning rhythm and piled cognitive load onto a high-frequency task.

### Design Goals

- **Reduce clicks to reach critical flight details** — body and bay type should be visible without expanding
- **Speed up flight identification at a glance** — controllers scan, not read
- **Cut stand-assignment errors** — ambiguity between remote and frontal should be impossible to miss

## Research & Discovery

There was no formal user-research programme on this phase. My understanding of controller workflow came from **direct observation and learning the operational mental model**: how controllers actually scan the board, what they look for first, and when they expand a flight versus when they just need to glance.

Two insights shaped the whole redesign:

1. **Body type comes first in a controller's mind.** It drives resource allocation, so controllers categorise flights by aircraft size before anything else. The interface should match that mental order.
2. **Scanning beats diving.** Controllers prefer to take in the whole board at a glance and only expand a flight when they're about to act — not to find out *what* a flight is.

From this, I distilled a single design principle:

> *Progressive disclosure aligned with controller workflow: show body type at a glance, reveal bay type on expansion.*

### Key Design Decisions

**Icon system for body types (collapsed view).** Wide-body and Narrow-body get distinct icons, so a controller can recognise aircraft size *without reading text*. This leverages pre-attentive visual processing — the whole board becomes scannable in seconds rather than read row by row.

**Color-coded bay type indicators.** Remote and Frontal stands are marked with distinct color dots. To avoid relying on color alone — which fails for color-blind users — I paired each color with an **icon and label**, so the distinction survives even without color perception.

**Tab separation in baseline settings.** The settings page splits Wide-body and Narrow-body baselines into separate tabs, reducing cognitive load when configuring default PTS events per aircraft type, with Remote/Frontal events keeping the same color system as the dashboard for consistency.

## Visual Design

Controllers stare at the board for long stretches, so the interface takes a **light enterprise-dashboard** direction — no decorative color, relying on information hierarchy and iconography to do the distinguishing.

### Color

- **Background:** light grey-white (`#F1F1F1` / `#DBDBDC` / `#FFFFFF`) — easy on the eyes over long shifts and lets colored status indicators stand out
- **Primary / headings:** deep navy (`#304666` / `#172333`) — used for titles, body-type icons, and expanded flight details
- **Bay-type status:** Remote and Frontal use contrasting color dots paired with an icon + label, so the distinction holds even for color-blind users

### Icon System

Wide-body and Narrow-body each get a distinct icon, so controllers recognise aircraft size without reading — leveraging pre-attentive visual processing to make the whole board scannable in seconds.

### Layout & Density

A high-density information board with row spacing kept tight but a scannable rhythm preserved. Collapsed view shows only the body-type icon and essential fields; expanded view reveals bay type and PTS details.

## Outcomes & Feedback

Controllers fed back that the redesign let them **see the information they needed more intuitively** — body type and bay type became visible at a glance instead of buried behind a click, which matched how they already scanned the board during peak hours.

## Reflections

Aligning the design hierarchy with the controller's mental model — body type first, bay type on demand — was the key. Using visual indicators (icons + color) for a high-frequency scanning task is what made the board readable at a glance. The biggest lesson: **understand the user's mental model before designing any information architecture**. The interface should follow how people already think, not force them to learn a new model.
